# API and Authentication

This document defines the AgentHub network surface: ConnectRPC/gRPC services,
HTTP endpoints, and the Shadow SSO integration. The browser login, landing-page
cards, web agent creation, and the Shadow SSO Kubernetes deployment are detailed
in [web-and-sso.md](web-and-sso.md).

---

## 1. Protocol choice

AgentHub uses **ConnectRPC** generated by `buf`:

- One Go handler serves **Connect**, **gRPC**, and **gRPC-Web**.
- The TypeScript plugin and browser use plain HTTP/JSON via `@connectrpc/connect`.
- Go clients (CLI, federation) use `connect-go`; native gRPC clients work unchanged.
- Streaming is available for catalog change events.
- Blob transfers are plain HTTP GETs, not RPC streams, so CDNs and range requests
  work normally.

This matches the PiLab ecosystem (`pirat-backend`, `shadow-sso`) and avoids a
separate gRPC gateway.

### 1.1 Ports and listeners

| Listener | Default | Purpose |
| --- | --- | --- |
| HTTP/Connect | `:8080` | Web, ConnectRPC, gRPC, blob downloads, skills catalog |
| Native gRPC (optional) | `:9090` | Internal/federation clients that require HTTP/2 gRPC |
| Metrics | `:9100` | Prometheus (private) |

In production, only `:8080` is exposed through ingress. The optional `:9090`
listener is for private network federation and can be disabled.

## 2. Services

### 2.1 `agenthub.catalog.v1.CatalogService`

Read-only catalog operations. Public assets are readable anonymously; private
spaces require a reader role.

| RPC | Request | Response | Notes |
| --- | --- | --- | --- |
| `SearchAssets` | query, filters, page | results + facets | Cursor pagination |
| `GetAsset` | full ref | asset + latest version | No version required |
| `ListVersions` | asset ref, page | versions | Newest first |
| `GetVersion` | full ref | version + manifest | Exact version |
| `Resolve` | desired assets, constraints, lock, compatibility | resolved graph | Used by CLI |
| `GetBundle` | manifest digest or full ref | manifest + file URLs | Pre-signed URLs |
| `GetInstallGuide` | full ref, harness, scope | Markdown | Rendered in store |
| `WatchCatalog` | filters, cursor | stream of events | Optional; plugin live updates |

### 2.2 `agenthub.registry.v1.RegistryService`

Write operations. Requires `agenthub.publish` (or `agenthub.admin`) plus a
namespace role.

| RPC | Purpose |
| --- | --- |
| `CreateNamespace` | Create a namespace (admin or approved self-service) |
| `GetNamespace` / `ListNamespaces` | Namespace metadata and caller roles |
| `BeginPublish` | Reserve `(asset, version)`, return upload URLs |
| `CommitPublish` | Upload manifest + signature, finalize version |
| `CreateDraft` / `UpdateDraft` / `DiscardDraft` | Web dashboard draft lifecycle |
| `PublishDraft` | Sign and publish a dashboard draft |
| `SetLandingVisibility` | Hide/show a published asset on the landing page |
| `ValidateBundle` | Server-side dry run without persisting |
| `YankVersion` / `UnyankVersion` | Hide/restore a version |
| `DeprecateVersion` | Mark a version deprecated with a note |
| `DeleteDraft` | Delete an unpublished draft |
| `RegisterSigningKey` / `RevokeSigningKey` | Namespace key lifecycle |
| `ListAudit` | Namespace audit log (maintainer/owner) |

### 2.3 `agenthub.federation.v1.FederationService`

Server-to-server and admin operations.

| RPC | Purpose |
| --- | --- |
| `GetHubInfo` | Public hub identity, keys, protocol version |
| `GetSnapshot` | Signed descriptor of a full catalog generation |
| `SyncChanges` | Signed catalog pages since cursor |
| `ListUpstreams` / `UpsertUpstream` / `DeleteUpstream` | Admin |
| `TriggerSync` | Force a sync (admin) |
| `ExportBundle` / `ImportBundle` | Offline/air-gapped transfer |

`GetHubInfo` is also exposed as `/.well-known/agenthub.json` for non-RPC clients;
snapshots and pages are also served as plain HTTP for mirroring.

### 2.4 `agenthub.identity.v1.IdentityService`

Minimal identity surface; the real identity lives in Shadow SSO.

| RPC | Purpose |
| --- | --- |
| `WhoAmI` | Subject, email, scopes, groups, namespaces/roles |
| `ListMyNamespaces` | Namespaces the caller can read/publish to |
| `GetTokenInfo` | Expiry, scopes, client ID (no token value) |

There is **no login, password, MFA, or user CRUD** RPC. Those are SSO concerns.

### 4.3 OpenCode skills catalog

OpenCode V2 can consume skills directly over HTTP without the plugin. AgentHub
implements the catalog format:

```json
{
  "skills": [
    {
      "name": "pilab-pirat-agent-orchestration",
      "version": "3",
      "files": [
        "SKILL.md",
        "references/agent-run.md",
        "references/custom-fields.md"
      ]
    }
  ]
}
```

- Base URL: `https://agenthub.pilab.hu/opencode/skills/`
- The entry `name` is the runtime skill ID; AgentHub uses the same
  `<namespace>-<name>` convention as the plugin, so both delivery paths expose
  one ID.
- Each file is served at `<base>/<entry-name>/<file>`.
- The entry must include `SKILL.md` (or `<entry-name>.md`) at its root.
- `version` increments whenever any file changes.
- The catalog only exposes skills the caller may read (public by default; private
  catalogs require a token and are not usable by OpenCode's unauthenticated HTTP
  loader in v1).
- Users can add it to `opencode.json`:

```json
{
  "skills": ["https://agenthub.pilab.hu/opencode/skills/"]
}
```

Agents, MCP servers, and tools still require the plugin or portable mode.

## 5. Authentication and authorization

### 5.1 Shadow SSO integration

Shadow SSO (`https://sso.pilab.hu`) is the only identity provider.

| Setting | Value |
| --- | --- |
| Issuer | `https://sso.pilab.hu` |
| Discovery | `/.well-known/openid-configuration` |
| JWKS | `/.well-known/jwks.json` |
| Audience | `auth.client_id` for user tokens; `agenthub` for service-account tokens |
| Token type | JWT access token |
| User info | `openid profile email` |
| MFA | Enforced by SSO policy, not AgentHub |

AgentHub caches JWKS with the SSO `Cache-Control` headers and refreshes on an
unknown `kid`. It never stores passwords, TOTP seeds, or recovery codes.

Shadow SSO issues authorization-code tokens with `aud` equal to the OIDC client
ID. Service-account (`client_credentials`) tokens use the requested audience and
are limited by the client's `allowed_audiences`. AgentHub therefore validates an
audience allowlist rather than a single hard-coded value.

### 5.2 OAuth clients

All clients are provisioned in Shadow SSO (via `ssoctl`, GraphQL, or the admin
UI) and recorded in deployment config; AgentHub does not create them at runtime.

#### Web (`agenthub-web`)

One confidential client serves both the browser frontend and the Go backend BFF.
The backend performs the code exchange; the browser only receives an opaque
session cookie.

```bash
ssoctl client register \
  --name "AgentHub" \
  --description "AgentHub web store and dashboard" \
  --type confidential \
  --redirect-uris "https://agenthub.pilab.hu/auth/callback" \
  --post-logout-redirect-uris "https://agenthub.pilab.hu/" \
  --scopes "openid,profile,email,agenthub.read,agenthub.publish,agenthub.admin" \
  --grant-types "authorization_code,refresh_token" \
  --token-endpoint-auth-method client_secret_basic \
  --require-consent true
```

`ssoctl` generates the client ID; treat it as opaque and put it in
`SSO_CLIENT_ID`. Store the one-time secret in OpenBao as `SSO_CLIENT_SECRET`.

Requirements: confidential, authorization code + refresh token,
`client_secret_basic`, exact redirect URI, PKCE sent by AgentHub, consent on
first login. Shadow SSO issues authorization-code tokens with `aud` equal to the
client ID; AgentHub validates that value. Service-account clients request
`aud=agenthub` explicitly.

The full registration, BFF login sequence, and Kubernetes deployment are in
[web-and-sso.md](web-and-sso.md).

#### CLI (`agenthub-cli`)

```json
{
  "client_id": "agenthub-cli",
  "name": "AgentHub CLI",
  "type": "public",
  "allowed_grant_types": [
    "urn:ietf:params:oauth:grant-type:device_code",
    "refresh_token"
  ],
  "allowed_scopes": [
    "openid", "profile", "email",
    "agenthub.read", "agenthub.publish"
  ],
  "allowed_audiences": ["agenthub"],
  "token_endpoint_auth_method": "none",
  "require_pkce": false,
  "require_consent": false
}
```

#### CI service account (`agenthub-ci`)

```json
{
  "client_id": "sa-agenthub-ci@pilab.iam.sso.dev",
  "name": "AgentHub CI publisher",
  "allowed_grant_types": ["client_credentials"],
  "token_endpoint_auth_method": "private_key_jwt",
  "allowed_scopes": ["agenthub.publish"],
  "allowed_audiences": ["agenthub"],
  "service_account_groups": ["agenthub:pilab:publisher"]
}
```

- Prefer `private_key_jwt` over a client secret for CI.
- Use one service account per repository/namespace, not one global publisher.
- Rotate keys via Shadow SSO; revoke the old key after the pipeline is updated.

#### Federation (`agenthub-federation`)

```json
{
  "client_id": "sa-agenthub-federation@pilab.iam.sso.dev",
  "allowed_grant_types": ["client_credentials"],
  "token_endpoint_auth_method": "private_key_jwt",
  "allowed_scopes": ["agenthub.federation"],
  "allowed_audiences": ["peer-hub.example"],
  "service_account_groups": ["agenthub:federation"]
}
```

The audience must match the target hub; create one service account per peer hub
(or one audience-scoped client per peer). The target hub validates both the token
and the signed catalog; transport auth alone is never sufficient.

### 5.3 Claims mapping

| Claim | Use |
| --- | --- |
| `iss` | Must equal the configured SSO issuer |
| `aud` | Must be in the configured allowlist: the web/CLI client ID for user tokens, `agenthub` for service-account tokens, or the hub's federation audience |
| `sub` | Stable principal ID; used in audit and namespace membership |
| `email`, `name` | Display only; never authorization |
| `scope` | Space-separated coarse scopes |
| `roles` | Global roles (e.g. `agenthub:admin`) |
| `groups` | Namespace roles: `agenthub:<namespace>:<role>` |
| `exp`, `nbf`, `iat` | Validity; 60s clock skew |
| `jti` | Replay/audit correlation |
| `acr`, `amr` | Optional step-up checks for destructive actions |

Namespace role convention:

```text
agenthub:pilab:reader
agenthub:pilab:publisher
agenthub:pilab:maintainer
agenthub:pilab:owner
agenthub:admin
```

### 5.4 Token validation

```text
1. Extract Bearer token.
2. Verify signature with JWKS (RS256/ES256; reject `none` and algorithm confusion).
3. Verify iss == config.issuer, aud is in the configured allowlist (web/CLI
   client ID for user tokens, `agenthub` for service accounts, peer hub for
   federation), exp/nbf with 60s skew.
4. Parse scope, roles, groups.
5. For private resources, check namespace role.
6. For destructive actions (yank, key revoke, namespace delete), require
   iat < 15 minutes or perform introspection; optionally require MFA (acr).
```

Revocation:

- Access tokens are short-lived (≤ 15 minutes recommended).
- Refresh tokens are revoked on logout and can be revoked by SSO admin.
- High-risk writes call the introspection endpoint and fail closed if it is
  unavailable, unless the deployment is explicitly offline.

### 5.5 Authorization matrix

| Action | Scope | Namespace role | Anonymous |
| --- | --- | --- | --- |
| Read public asset | — | — | yes |
| Read private asset | `agenthub.read` | reader+ | no |
| Download public bundle | — | — | yes |
| Download private bundle | `agenthub.read` | reader+ | no |
| Publish a version | `agenthub.publish` | publisher+ | no |
| Create/edit a draft | `agenthub.publish` | publisher+ | no |
| Publish a draft | `agenthub.publish` | publisher+ (maintainer+ if review) | no |
| Hide/show landing card | `agenthub.publish` | maintainer+ | no |
| Enable hosted signing | `agenthub.admin` | owner | no |
| Yank/deprecate | `agenthub.publish` | maintainer+ | no |
| Manage install guides/metadata | `agenthub.publish` | maintainer+ | no |
| Register/revoke signing keys | `agenthub.admin` | owner | no |
| Create namespace | `agenthub.admin` | — | no |
| Manage upstreams | `agenthub.admin` | — | no |
| Read audit log | `agenthub.read` | maintainer+ | no |
| Admin all | `agenthub.admin` | — | no |

Deny by default. A missing role is a denial, not a fallback.

### 5.6 Web session

- Authorization code + PKCE + `state` + `nonce`.
- Tokens stored server-side in Valkey; the browser gets an opaque, encrypted,
  `HttpOnly`, `Secure`, `SameSite=Lax` session cookie.
- Session TTL 12 hours; idle timeout 30 minutes; rotate the session ID on login.
- CSRF double-submit token for all state-changing forms.
- Logout calls the SSO `end_session_endpoint` with `id_token_hint` and the
  registered `post_logout_redirect_uri`, revokes the refresh token, and deletes
  the local session.
- The web app never exposes access/refresh tokens to JavaScript.

### 5.7 CLI session

- `agenthub login` starts the Shadow SSO device flow with `client_id=agenthub-cli`.
- Prints `verification_uri_complete` and polls the token endpoint.
- Refresh token stored in the OS keychain:
  - macOS Keychain
  - Linux Secret Service / `pass` fallback
  - Windows Credential Manager
- If no keychain is available, a `0600` file is used only with an explicit
  warning; CI should use `AGENTHUB_TOKEN` or a service-account key instead.
- Access token is kept in memory; refresh happens 60 seconds before expiry.
- `agenthub logout` revokes the refresh token and clears local credentials.

### 5.8 Federation authentication

- Hub-to-hub calls use a Shadow SSO service account with `private_key_jwt` and
  audience = target hub.
- Optional mTLS via PiTrust certificates for defense in depth.
- The target hub checks: token signature/audience/scope, upstream allowlist,
  signed catalog page, and per-asset signatures.
- A compromised upstream token cannot forge an asset signature, and a forged
  catalog page cannot pass the hub signature check.

## 6. Error model

ConnectRPC status codes:

| Code | Meaning in AgentHub |
| --- | --- |
| `invalid_argument` | Schema/validation failure; details list field paths |
| `unauthenticated` | Missing/invalid/expired token |
| `permission_denied` | Scope or namespace role missing |
| `not_found` | Asset/version/namespace absent or not visible |
| `already_exists` | Version already published |
| `failed_precondition` | Lock/signature/state conflict; details explain |
| `resource_exhausted` | Rate limit, quota, or bundle size |
| `unavailable` | Upstream/SSO/storage temporarily unavailable |
| `internal` | Unexpected; correlation ID only, no secrets |

Error details use `google.rpc.ErrorInfo` with:

```json
{
  "reason": "SIGNATURE_INVALID",
  "domain": "agenthub.pilab.hu",
  "metadata": { "key_id": "ed25519:9f2c…", "manifest_digest": "sha256:…" }
}
```

## 7. Pagination, idempotency, concurrency

- **Pagination:** opaque cursor, default 20, max 100. Cursors are signed and
  expire after 24 hours.
- **Idempotency:** `BeginPublish`/`CommitPublish` accept `Idempotency-Key`; a
  repeated key returns the original result for 24 hours.
- **Optimistic concurrency:** asset metadata updates use `If-Match` with the
  asset's `updated_at`/ETag; versions are immutable and need no ETag.
- **Rate limits:** per IP for anonymous reads, per subject for authenticated
  calls, per namespace for publishes. Defaults:
  - anonymous search: 60/min/IP
  - authenticated read: 600/min/subject
  - publish: 30/hour/namespace
  - federation sync: 10/min/upstream
- **Request size:** RPC bodies ≤ 4 MiB; manifests ≤ 1 MiB; blobs go to S3.
- **Timeouts:** read RPC 10s; resolve 15s; publish commit 30s.

## 8. Versioning

- Proto package versions are `v1`; breaking changes require `v2`.
- `buf breaking` runs against the previous release in CI.
- HTTP endpoints are versioned under `/v1/` where they are not HTML.
- The OpenCode skills catalog is versioned by the `version` field per skill, not
  by URL.
- Deprecated fields are annotated and kept for at least one minor release.
